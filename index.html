Why we built it

Agents now write in minutes what takes hours to read. The tools we read code with were built for a different job. Here is how we got here, and why we think the next IDE is one you read.

Writing used to be the slow part.

For forty years, every tool around the editor existed to make writing faster, or to help you find your way around code you already knew.

  • Autocomplete
  • Snippets
  • Go to definition
  • Find usages
  • Rename symbol
  • The file tree

None of them tells you what a part of the program is for. You knew that already: you wrote it.

Then writing got cheap.

On 4 November, Claude Code added saved sign-ins to Mira’s Preview. Twelve files and 867 new lines, in one sitting. This is what reviewing it looks like from a terminal.

Reading didn’t get faster.

In a 2025 study, experienced open-source developers took 19% longer to finish real tasks with AI tools. They had expected to be 24% faster, and afterwards they still believed they had been 20% faster.

In Stack Overflow’s 2025 survey, 66% of developers said AI answers are “almost right, but not quite”, and 45% said debugging AI-generated code takes longer. Only 3% highly trust what it writes.

The IDE still shows you files.

Two pieces from October 2026 argue that we still need an IDE: for diffs, for finding your way, for checking. We agree about the problem. But go to definition, find usages and the file tree were built for code you already know. For code you didn’t write, what’s missing is what each part is for and how the parts connect.

Here is the same change again. Twelve files is a list you read top to bottom. On the map it’s two parts of the product, and inside one of them, four.

So we built the map.

Reading every line doesn’t scale to the speed agents write at. Reading at the right height does: the shape of the program first, then the lines only where the shape changed, or where the risk is.

Code maps have been tried before. They were something you opened once, when you joined a team. Agents changed that: now there is code you didn’t write every day, and someone still has to own it.

Mira sits beside your editor and your agent, and replaces neither. It’s the part you read.

Solid means checked. Dashed means guessed.

A map you can’t trust is worse than none. Sentences that fail the check are taken out before you see them, and what the map couldn’t prove is marked, so you know what to read yourself.

  • Handling RequestsChecked

    Every sentence on a plain card was checked against the lines it cites. Plain cards carry no badge.

  • Handling RequestspartialPartial

    Found in the code, and known to be incomplete. The card says what is missing.

  • Handling RequestsinferredInferred

    Not provable from the code, so drawn dashed, the way a map draws a boundary nobody has surveyed.

Questions.

Is this an IDE?

No. Keep the editor you use. An editor shows one file at a time and an agent panel one message at a time; Mira shows how the whole repository fits together and what a change did to it. It opens the code where you need it, and hands your questions to the agent beside it.

Does my code leave my Mac?

Only the way it does whenever you use Claude Code: your own Claude Code reads the files it needs to make the map. The map itself is saved on your Mac and nowhere else.

What do I need?

A Mac, and Claude Code signed in with a Claude plan. Making a map counts against that plan's usage, like any other Claude Code session.

Which languages does it read?

TypeScript, JavaScript, Python, Go, Ruby, Rust, Java, Kotlin, Scala, Swift, PHP, C# and Elixir, along with Vue, Svelte and Astro components, and the SQL, Prisma, GraphQL and protobuf files around them.

How do I tell what's proven from what's a guess?

A solid line or a plain card came from the code. Anything the map couldn't prove is marked: a dashed line, or a card labelled partial or inferred. Sentences that failed the check are taken out before you see them.

What happens when the code changes?

An update finds the files that changed since the map last looked, redoes only the sections whose code they touch, and moves every other line reference along with the code, so the rest stays true.
